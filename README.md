# Jira QA Pulse

Локальный Java-дашборд с двумя разделами. **Очередь QA** показывает задачи, ожидающие проверки, и историю их переходов. **Сбои отчётов** связывают исходный прогон, подтверждённую причину, повтор и операции на тестовом стенде. В проекте используются демонстрационные выгрузки, которые можно редактировать вручную. Jira и CI в этой версии представлены этими файлами.

## Запуск

Нужен JDK 17 или новее. Распакуй архив, открой терминал Windows в папке проекта и запусти сервер на порту 8090.

```powershell
.\run.cmd 8090
```

Открой [http://127.0.0.1:8090](http://127.0.0.1:8090). Подставь другой номер в команду, чтобы выбрать порт. Для остановки нажми Ctrl+C. Проект собирается средствами JDK. Сервер использует локальный интерфейс, данные читает при старте.

Тесты запускаются отдельной командой.

```powershell
.\run.cmd -Test
```

## Подключение Jira

Jira QA Pulse читает срез из файлов в папке `data/`. Инструкция ниже показывает, как получить задачи и историю из Jira REST API, сохранить их в нужном формате и загрузить в дашборд. Команды можно вводить прямо в PowerShell.

### Jira Cloud

1. Возьми адрес сайта Jira, email учётной записи Atlassian и ключ проекта, например `SHOP`. У учётной записи должен быть доступ на просмотр проекта и нужных задач.
2. Создай API-токен в настройках аккаунта Atlassian. Для токена с областями доступа выбери права чтения задач и истории. Используй базовый адрес `https://api.atlassian.com/ex/jira/{cloudId}`. Свой `cloudId` можно получить по адресу `https://team.atlassian.net/_edge/tenant_info`. Для обычного токена используй адрес сайта `https://team.atlassian.net`. [Создание токена](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/) · [Где найти Cloud ID](https://support.atlassian.com/jira/kb/retrieve-my-atlassian-sites-cloud-id/)
3. Подставь свои значения и выполни поиск задач. Когда `curl.exe` запросит пароль, введи API-токен.

```powershell
$jiraBase = 'https://team.atlassian.net'
$jiraEmail = 'you@example.com'
$jiraProject = 'SHOP'

curl.exe --fail --user $jiraEmail --get `
  --data-urlencode "jql=project = $jiraProject ORDER BY created ASC" `
  --data-urlencode "fields=summary,created,status" `
  --data-urlencode "maxResults=50" `
  "$jiraBase/rest/api/3/search/jql"
```

Если ответ содержит `nextPageToken`, добавь его в следующий запрос как параметр `nextPageToken`. Для каждой задачи получи историю отдельным запросом. В ответе понадобятся записи `values`, время изменения `created` и элементы `items`, где `field` равно `status`. Пока `isLast` равно `false`, запрашивай следующую страницу. Для нового `startAt` прибавляй к текущему смещению число полученных записей в `values`. [Поиск JQL](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/#api-rest-api-3-search-jql-get) · [История задачи](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/#api-rest-api-3-issue-issueidorkey-changelog-get)

```powershell
$jiraIssue = 'SHOP-142'
curl.exe --fail --user $jiraEmail --get `
  --data-urlencode "startAt=0" `
  --data-urlencode "maxResults=50" `
  "$jiraBase/rest/api/3/issue/$jiraIssue/changelog"
```

### Jira Data Center

Создай персональный токен в профиле Jira. Используй адрес своей инсталляции целиком, включая путь вроде `/jira`, если он есть. В запросе поиска передай `expand=changelog`, чтобы получить историю вместе с задачами. В окне PowerShell введи токен в поле пароля. [Персональные токены](https://confluence.atlassian.com/enterprise/using-personal-access-tokens-1026032365.html) · [REST API поиска](https://developer.atlassian.com/server/jira/platform/rest/v10006/api-group-search/)

```powershell
$jiraBase = 'https://jira.example.com'
$jiraJql = [Uri]::EscapeDataString('project = SHOP ORDER BY created ASC')
$jiraPat = Get-Credential -UserName 'pat' -Message 'Введи персональный токен Jira'
$jiraHeaders = @{ Authorization = 'Bearer ' + $jiraPat.GetNetworkCredential().Password }

Invoke-RestMethod -Headers $jiraHeaders `
  -Uri "$jiraBase/rest/api/2/search?jql=$jiraJql&fields=summary,created,status&expand=changelog&maxResults=50&startAt=0"
```

Для следующих страниц задач используй `startAt`. Бери изменения статуса из `changelog.histories` и проверяй полноту истории перед расчётом интервалов.

### Подготовка данных для дашборда

1. В `data/issues.tsv` запиши одну строку на задачу. В `initialStatus` укажи статус на момент создания. Возьми предыдущий статус из самого раннего перехода, а при отсутствии изменений статуса используй текущий.
2. В `data/transitions.tsv` добавь каждое изменение статуса, включая повторные заходы в QA. В колонке `to` запиши статус назначения. Сопоставь статусы Jira с кодами приложения.

| Этап в Jira | Код в TSV |
| --- | --- |
| Бэклог или новая задача | `BACKLOG` |
| В разработке | `DEVELOPMENT` |
| Готово к тестированию | `READY_FOR_QA` |
| На проверке | `IN_QA` |
| Готово | `DONE` |

Пример `data/issues.tsv`.

```tsv
key	title	createdAt	initialStatus
SHOP-142	Восстановление корзины	2026-11-19T08:00:00Z	DEVELOPMENT
```

Пример `data/transitions.tsv`.

```tsv
issueKey	at	to
SHOP-142	2026-11-20T04:00:00Z	READY_FOR_QA
```

3. Сохрани TSV в UTF-8, разделяй колонки табуляцией и переведи даты Jira в UTC в формате ISO 8601. Укажи код проекта и время выгрузки в `data/snapshot.properties`, например `project=SHOP` и `asOf=2026-11-20T10:00:00Z`.
4. Для запуска только с данными Jira оставь заголовки в `runs.tsv`, `diagnoses.tsv` и `actions.tsv`. Это уберёт демонстрационные связи с задачами. Запусти дашборд командой `.\run.cmd 8090`. После следующей выгрузки перезапусти приложение, чтобы оно прочитало новый срез.

### Данные CI для раздела «Сбои отчётов»

| Файл | Что взять из CI или разбора |
| --- | --- |
| `data/runs.tsv` | ID прогона, ключ Jira из `issues.tsv`, время, инициатор, результат генерации отчёта и ID исходного прогона для повтора |
| `data/diagnoses.tsv` | Причина, подтверждающий фрагмент лога и имя сотрудника для причины `QA_INPUT` |
| `data/actions.tsv` | Перезапуск или развёртывание, длительность и номер сбоя, с которым операция связана по журналу CI |

Ключ Jira связывает задачу с прогоном. Для операций на стенде сохраняй отдельную ссылку на исходный сбой через `causedByRunId`. У плановых операций это поле пустое. Храни API-токен отдельно от TSV и исходников проекта.

## Демо на собеседовании

1. В очереди открой **SHOP-142**. В первый заход задача ждала 18 часов и провела 3 часа на проверке. После возврата разработчикам она снова попала в очередь. На момент среза текущий заход длится 6 часов, суммарное ожидание составляет 24 часа.
2. Перейди в **«Сбои отчётов»**, открой **№315**. Лог подтверждает ошибку профиля тестовых данных. У исходного запуска инициатор Алексей, у повтора №316 инициатор CI. Запись D11 связывает развёртывание с исходным сбоем и показывает 8 минут работы стенда.
3. Открой **№317**. Ирина указала неверный путь к результатам, а повтор запустил Алексей. Ошибка учтена у Ирины, запуск Алексея отображается в истории повторов.
4. Сравни **№319** и **№321**. В первом есть связанный перезапуск по причине сбоя стенда. Во втором причина ещё выясняется. Плановое развёртывание D13 в повторном прогоне №322 отсутствует в статистике связанных операций, поскольку в источнике оно помечено как плановое.

## Правила подсчёта

- Текущее ожидание начинается с последнего входа в `READY_FOR_QA`. Суммарное ожидание включает все интервалы в этом статусе до среза. Время проверки считается по интервалам `IN_QA`.
- Возврат в разработку — прямой переход из `IN_QA` в `DEVELOPMENT`. Статистика очереди использует всю историю загруженных задач до среза.
- Период в разделе сбоев определяется временем начала исходного прогона. Его прямые повторы и связанные операции показываются по состоянию на момент среза. Сумма времени операций — длительность записанных работ на стенде.
- Для ошибки запуска QA требуется запись разбора с причиной `QA_INPUT`, именем и подтверждением из лога. Отсутствующая причина отображается как «На разборе».
- Перезапуск сервиса и развёртывание учитываются по разным типам событий. Чтобы операция на стенде попала в разбор сбоя, в исходных данных нужен ID этого сбоя и последовательность связанных повторов.
- Фильтр причины сужает таблицу сбоев. Верхняя сводка и разрез по тестировщикам показывают весь выбранный период.

## Данные и сервер

| Файл | Содержимое |
| --- | --- |
| `data/snapshot.properties` | Код проекта и время среза в UTC |
| `data/issues.tsv` | Задачи, дата создания и начальный статус |
| `data/transitions.tsv` | История переходов задач |
| `data/runs.tsv` | Прогоны, авторы запуска, ссылки на повторы, результат формирования отчёта |
| `data/diagnoses.tsv` | Подтверждённые причины и фрагменты логов |
| `data/actions.tsv` | Операции на стенде, длительность и связь с исходным сбоем |

Таблицы разделены табуляцией и сохранены в UTF-8. Время записано в ISO 8601. `PulseData` читает и проверяет ссылки в файлах, `PulseReport` считает метрики, `PulseServer` отдаёт интерфейс и JSON. Интерфейс запрашивает `GET /api/queue` и `GET /api/failures?days=7`. Для сбоев также доступны значения периода `30` и `all`.
